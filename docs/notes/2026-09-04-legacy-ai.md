# Behaviour note: legacy skirmish AI (2026-09-04)

Derived from behavioural analysis of the retail binary. `:NNNNN` citations are
evidence pointers into a private reference that is not distributed — they mark where a claim can be re-checked by whoever holds it,
and nothing here reproduces that file's expression.

Symbol names marked *(tool-assigned, misleading)* are automatic labels
that do **not** describe what the routine does; the description beside them
does. In this region most labels are wrong — the build-selection code is
labelled as formation code, and the AI-profile loader is labelled as feature
animation.

## Architecture

Each player owns two AI structures.

**AIBrain** — one per player slot, living inside the player record, created at
`AIBrain_Init` :19382. Its fields, by role:

| Field | Meaning |
|---|---|
| Group slot array | ~100 slots; the strategic layer (below) |
| Unit round-robin cursor | Which unit the per-tick sweep resumes from |
| Group-tick counter | Cadence counter for group updates |
| "Base under attack" timer | Game-time stamp until which builders stay frozen |
| Bootstrap flag | Set during the opening seconds, gates the opening branch |

**AI weight/limit table** — one per player, held in a fixed global array indexed
by player (the reference tooling attributes it to an unrelated debug-timing global —
misleading). Built by `AIBrain_InitBuildOrders` :19604. It is a set of parallel
per-unit-type arrays, each sized to the number of unit types loaded:

| Per-type array | Meaning |
|---|---|
| Build score | Computed 0..100 desirability input (see "Build decision") |
| Owned count | Instances existing, including under construction |
| Completed count | Instances finished |
| Combat value | Per-type combat strength, summed for threat estimates |
| Static bonus | +40 when a unit-def classification field is zero; +20 when the type has a build list. (The dig cites that field by raw offset only — its meaning is **not** established; see Open questions.) |
| Profile `weight` | 0..100, from the AI profile file |
| Weight lock | Set once a profile line has set the weight |
| Profile `limit` | Max instances; -1 = unlimited |
| Limit lock | Set once a profile line has set the limit |
| Total owned | Running total across all types |
| Visibility vectors | Visible enemies / allies / enemy structures / own defences, rebuilt by `AIBrain_EvaluateMap` |
| Base grid spacing | Per-player randomised placement grid (see "Placement") |

### Per-tick flow

The per-player AI step runs from the 30 Hz simulation tick, out of
`Sim_UpdatePlayers` *(tool-assigned name refers to feature height —
misleading)* :206584:

1. `AIBrain_Think` :19335. When the player's controller kind is 2 it also runs
   `AIBrain_UpdateGroups` :19300.
2. `AIBrain_RunTick` :18938 always runs; it round-robins
   `(worldUnitCount / 30) + 1` units per tick, so every unit is visited roughly
   once per second regardless of army size.
3. `AIBrain_TryUpdateAttackPlan` gates `AIBrain_UpdateAttackPlan` :20616 to at
   most once every 7 ticks. That rebuilds the LOS-gated enemy lists via
   `AIBrain_EvaluateMap`; 1 time in 30 it additionally runs
   `AIBrain_EvaluateEconomy` (so the build decision fires roughly every 7
   seconds), then re-counts through `AIBrain_PlanAttack` :20577.

## Groups (the strategic layer)

Every unit carries a group id. Assignment to a group reuses the transport
pickup entry point — `Unit_PickupForTransport(unit, groupId)`
*(tool-assigned, misleading: it is assign-to-group, not transport)*.

| Group id | Role |
|---|---|
| 0 | Unassigned |
| 1 | Builder pool (bootstrap) |
| 2..20 | Strategy / build-expedition groups (`AIBrain_UpdateStrategy` :16187) |
| 21..49 odd | Short-range attack groups, engagement radius 200000 (`AIGroup_UpdateAndDispatch` :18250 / `AISearch_UpdateThreatMap` :18632) |
| 51..79 odd | Long-range / air raid groups, radius 500000 |
| 81..95 | Build-queue behaviour |
| 96 | Idle |
| 0x61, 0x62 | Mass attack; 0x62 uses radius 1,000,000 |

Group state is five named slots plus a mode:

| Slot | Meaning |
|---|---|
| Target id | Encoded: positive *n* = start position *n*−1; negative *n* = sacred site −*n*−1. Resolved by `AISearch_ResolveTarget` :17079 |
| Requested-strength threshold | Ratcheted up over time (see "Attack waves") |
| Launch threshold | Group waits until its member count exceeds this |
| Assigned count | Members the strategy layer allotted |
| Leader / target | Unit id |
| Mode | 0 idle, 1 engaged, 2 marching |

## Expansion targets

- **Sacred sites** are a fixed-size record table built at map load :128256 from
  every map feature whose feature-TDF key `sacredsite` is non-zero (key parsed
  at :127337 into the feature definition). Each record holds an active flag and
  an x/z map position. These are the Lodestone spots.
- **Player start positions** live in a parallel map-load table, indexed by a
  per-player start-position index. (The reference tooling's global names for both
  tables are misleading — one is labelled as a count.)

## LOS honesty — no AI cheating

`Player_CanSeeUnit` *(tool-assigned name refers to feature rendering —
misleading)* :206797 samples the requesting player's own LOS bitmap, which the
player record carries together with its width and height. Every AI enemy list
is gated through it (:20531-20540).

- **No vision cheat.** The AI sees only what its LOS grants.
- **No mana cheat.** The AI aborts and throttles builds on the same mana
  fractions a human faces — below 0.2333 and below 0.7 (:9391, :12127, :31415).
- The **only** asymmetry: an AI builder that takes damage freezes construction
  for 1-31 seconds (:15092-15096). The freeze timer is set to
  `gametime + 30 + 3 × rand(300)` ticks and stored in the brain's
  "base under attack" field.

## AI profile format (`data/ai/*.txt`)

**The profile is a console-command file**, not a structured config. It is
loaded by `AI_LoadProfiles` *(tool-assigned name refers to feature
animation — misleading)* :206363, from `ai\<aiprofile>.txt` where `aiprofile`
is a mission-TDF key (:169124-169131), falling back to `ai\default.txt`. Each
line is executed as a console command. Three commands are registered for it
(:14991): `plan`, `weight`, `limit`.

```
weight <unitname-or-category> <float>   ; 0..100 clamped, all brains
limit  <unitname-or-category> <int>    ; max count; -1 = unlimited
```

- Name lookup (:230881) tries the exact unit type name first; failing that it
  resolves a named category to a 512-bit type mask and applies to every type in
  the mask.
- Both commands set a per-type lock. Types left unlocked fall back to the FBI
  key `ai_weight` — a 64-character string on the unit definition, parsed at
  :162560 and itself executed as a console line (:20193/:20238).
- A malformed line emits `parse error reading AI profile %s...` :159930 and
  **aborts the rest of the file**.
- The profile is per-map/mission and shared by every AI player in the game.
- The 19 shipped profiles contain only `weight`, `limit` and comments. Typical
  content: `weight aradrag 25`, `weight arawall 0`, `limit aralode 7`,
  `limit aradrag 1`, `limit arabuild 10`.

### Mission-TDF per-player AI knobs (:169026-169131)

Under `[Player<i>]`, one value string is substring-matched for:
`strategic` | `passive`; `opponent` | `ally` | `neutral`; a `<sidename>`;
`logo <i>`; and **`massattack <seconds>`** (multiplied by 30 to give the tick
of the all-out attack). Alongside are `killmul` / `timemul` floats and
`aiprofile <name>`.

## Build decision (`AIBrain_EvaluateEconomy` :19859, ~every 7 s)

The AI scores every candidate type, then picks by weight. Two inputs are
computed first:

- **manaFrac** = the player's current mana divided by its maximum.
- **stalling** — true when (average income − average spend) is below −0.01, or
  when that difference is approximately zero *and* current mana is below 0.01.

Adjustments are applied in this order to a per-type score:

| # | Condition | Effect |
|---|---|---|
| 1 | Always | Score starts at **1** |
| 2 | Type carries the combat-unit flag | Score is set to **21** (a flat base, not an addition) |
| 3 | Type carries the economy-building flag **and** owned == completed (nothing of the type currently under construction) | One limit band below is added |
| 3a | Profile `limit` < 3 (a deliberately rare type) | **+15**, divided by **3** while stalling |
| 3b | owned ≤ limit / 4 | **+30**, divided by **2** while stalling |
| 3c | owned ≤ limit / 2 | **+10**, divided by the stall divisor |
| 3d | otherwise | **+6**, divided by the stall divisor |
| 4 | Candidate is a mana-producing building and manaFrac < **0.01** | **+30** |
| 5 | Candidate is a mana-producing building and manaFrac < **0.30** | **+30** (cumulative with 4 — below 0.01 the type gets +60 total) |
| 6 | Build cost > **500** | Tiered random subtractions, scaled by current army size — the tiers compare the owned count against a random draw such as `rand(30) + 10`, so a small army suppresses expensive types and a large one does not |
| 7 | owned == 0 | Score **× 4** |
| 8 | owned == 1 | Score **× 2** (mutually exclusive with 7) |
| 9 | Unit-def special-ability index ≥ 0 (the same field that marks role 6 "special" units) | Score **× 3** |
| 10 | Type carries the never-auto-build flag (set on the Monarch) | Score forced to **0** |
| 11 | Candidate is a mana-producing building **and** (manaFrac ≥ 0.30, **or** not stalling, **or** owned > completed) | Score forced to **0** |
| 12 | Always, last | Clamp to **0..100** |

The bands in step 3 are evaluated in order and the first match wins.

Two consequences worth stating, because they are easy to miss when
implementing:

- Rule 11 means a mana building is only ever a candidate while mana is below
  0.30, the economy is stalling, and none is already under construction — i.e.
  **one mana building at a time**, built only under actual pressure. Any mana
  building that survives rule 11 therefore always collected the +30 from rule 5.
- Rules 7 and 8 are the "first of type" pacing: the very first instance of
  anything is worth four times its steady-state score, the second twice. This
  is what makes the legacy AI diversify its build instead of spamming one type.

**Pick:** `desirability = weight[type] × score[type] / 100`
(`AI_BuildDesirability` :21281). The winner is chosen by **weighted reservoir
sampling** over the builder's build list (:21300) — structures and mobiles are
sampled separately — so the choice is randomised, not a maximum.

### Placement (:21419)

- Types anchored to sacred sites go to `AIBrain_FindBuildSite` :20447, which
  picks the nearest valid site.
- Everything else goes to `AIBrain_EvaluateBuildTarget` :20311: **30 random
  polar attempts**, each snapped to a **randomised per-player grid**
  (`AIBrain_UpdateScoring` :20283 — spacing `6 + rand(10) + 8` for structures,
  `9 + rand(20) + 8` for mobiles, plus jitter), rejecting any cell occupied by
  a sacred site.

## Unit / factory / builder think

- **Mobile builders** (:17163, `AISearch_ProcessCandidates`
  *(tool-assigned, misleading)*): retreat when hurt → build a structure →
  build a mobile → fall through to combat think.
- **Factories** (:17983): when idle and manaFrac ≥ 0.2333, pick and queue.
  Candidates costing over 500 are randomly skipped while mana is below 0.7.
- **Combat / idle units** (:17624): pick a target from the visible-enemy list;
  with nothing visible, wander near the base between two waypoints.
- **Group cohesion** (:15801): eject the furthest outlier repeatedly until the
  group's spread is at most `memberCount × radius`.
- **Roles** (:15514, `AIUnit_MatchesRole`): 0 = any · 1 = under construction ·
  2 and 3 = production structures · 4 = ground combat · 5 = air (the unit-def
  air flag) · 6 = special (the unit-def special flag together with a positive
  special-ability index) · 7 = non-builder.

## Attack waves (`AIBrain_UpdateStrategy` :16187)

Reschedules itself `rand(30) + 15` ticks out. Each pass counts spare units per
role against the group thresholds, which **ratchet upward over time**: when a
group's requested-strength threshold is below
`totalOwned / (builderGroup ? 20 : 30)`, every threshold on that group is
raised by `rand(threshold / 2) + 1`.

- **Spare builders → expansion.** `AIBrain_DecideBuildOrder` :16503 picks a
  builder (role 3 first, then role 2), scans the sacred-site table, and takes
  the nearest safe unclaimed site — skipping sites already targeted by another
  group and sites where `enemiesWithin(50) × 3` exceeds the allowed threat.
  It assigns the builder plus a ground and/or air escort.
- **1 pass in 10** instead reinforces the nearest under-strength threat or
  support group.
- **Spare ground units → a new group** (next free odd id in 21..49). Its
  assigned count is set to the number of spare units, and its **launch
  threshold is `rand(count × 2 / 3)`** — a randomised fraction of the intended
  size, so waves launch early and at varying strength.
- **Spare special units → a new group** in the odd 51..79 band.

**Execution** (`AIGroup_UpdateAndDispatch` :18250) reschedules `+15..75` ticks,
or `+150..1050` when it has no target:

- If the group's member count is at or below its launch threshold, the group
  disbands back into its parent — the wave was not ready.
- Otherwise it selects a target via `AIGroup_SelectAttackTarget` :15365, whose
  score is approximately `INT_MAX` divided by randomly smoothed distances, with
  the result divided again by `rand(1..20)` when the target is **not** visible.
  Non-visible targets are therefore heavily but not absolutely deprioritised.
- Then it path-checks and either attacks (mode 1) or marches (mode 2).
- Members below **¾ max HP are ejected** from the group on every pass (:18364).

Other behaviours in this layer:

- **Raid groups with nothing to do march to a random map edge or corner**
  (:18632). This *is* the legacy scouting behaviour — there is no separate
  scout logic.
- **Bootstrap** (:18748, game time < 31 ticks): every builder is put in group 1.
- **Mass attack**: a per-player countdown, seeded from the mission's
  `massattack <seconds>` key, is stored in the brain table. When it elapses,
  every mobile non-builder is forced into group 0x62 — the all-out attack
  (:18880-18895).
- **Engagement radius** (:17400): `max(sqrt(groupStrength) / 2, 5 × rangeClass)`
  converted to world units by a ×16 fixed-point shift. `rangeClass` comes from
  a four-entry table `{14, 10, 7, 5}` selected by unit class (:17428) — **not**
  by difficulty. Below ¼ HP the radius is divided by 5, with a floor of 160
  (:17705).

## Difficulty

**There is no AI difficulty setting in Kingdoms.** The debug dump prints
"no difficulty in Kingdoms" (:21519; string at :1383). All legacy tuning is
done by swapping the AI profile and by the `massattack` timer. Our
`TAK_AI_PursuitRadius` 50/100/150/200 % model has **no legacy counterpart** —
it is an invention of ours.

## Gap list vs `src/game/ai.c` (impact-ordered)

1. No AI profile loading — `weight × score` **is** the build decision; we build
   first-match instead.
2. No limit enforcement (legacy caps such as `aralode 7`, `aradrag 1`).
3. No sacred-site expansion. Legacy sends builders plus escort to claim sites;
   we build exactly one economy building, ever, in a blind ring.
4. No wave assembly or launch threshold — we trickle units individually to the
   enemy start position.
5. No mass-attack timer.
6. No defence building or defence awareness. Legacy tracks its own towers and
   uses that in placement and reinforcement decisions.
7. No scouting and no threat map. Legacy sends raid groups to random map edges;
   threat is the summed combat value within a radius (:20857).
8. Our decisions are fully deterministic. Legacy randomises the build pick, the
   placement, the target selection and the cadence of every layer.
9. No economy throttle or stall handling — the 0.01 / 0.30 / 0.2333 / 0.70
   gates, one mana building at a time, the >500-cost brake.
10. No first-of-type ×4 / ×2 pacing.
11. Wrong difficulty model. Keep the API for the launcher, but re-derive the
    radius from the unit-class range table.
12. No group cohesion or retreat — the ¾-HP ejection, the hurt-builder retreat.
13. No base-under-attack construction freeze.
14. Placement fidelity — legacy's randomised grid versus our spiral ring.
15. Campaign AI is disabled in ours; legacy runs the same brain with
    campaign-only bootstrap branches.
16. Tests to add once profile loading lands: profile parse, limit capping,
    desirability formula, sacred-site selection.

## Open questions

- The **static bonus** condition "+40 when a unit-def classification field is
  zero" is cited only by raw field offset in the source dig; what that field
  classifies is unresolved. The +40/+20 values and the "has a build list"
  condition are solid.
- Steps 3c and 3d of the build score are recorded in the source dig with their
  stall divisors elided. Bands 3a and 3b divide by 3 and 2 respectively;
  whether 3c/3d reuse 2, or something else, must be re-checked at :19859
  before implementing.
