# Replays (2026-09-30)

Issue #294 asked for two things: watching a match live, and replays. This
note covers the replays. Watching live is later work.

## What a replay is

A lockstep battle is a pure function of three things: the battle
configuration with its seed, the engine and data that run it, and the
commands its queue applies. A replay records the first and checks the
second, and it records the third as the queue applies it. Nothing else
goes in. The AI gives no commands through the queue, because every
machine runs it from the seed, and so does playback.

The recorder sits on the command queue's observer, which sees every
command the moment before it is applied and in the order it is applied,
whether it came from this machine or from the relay. The command already
carries the tick it ran on and the seat it belongs to, so a match and a
skirmish are recorded by the same few lines.

## When a battle is recorded

A skirmish or a match is recorded when the battle screen opens on a
world at tick zero. A campaign mission is not, because its script and
placements are not in the header. A battle loaded from a save is not,
because it starts part way through and a replay starts from the seed.
The `RecordReplays` setting turns recording off when it is 0. Under one
second of battle is deleted on close.

The file goes in the saved game directory as `YYYYMMDD-HHMMSS.okreplay`,
from the time the battle started in UTC. In a browser that directory is
the one the page already copies to origin private storage, so a replay
is kept the way a save is kept, and the page's Saved games panel writes
one out to a file and reads one back.

While a battle records, the file is flushed every 10 checkpoints, ten
seconds, and in a browser the page is asked to copy it to storage at the
same time. A tab that closes loses ten seconds of battle at most.

## How much is kept

The directory keeps the newest 30 replays within 48 MB
(`TAK_REPLAY_KEEP`, `TAK_REPLAY_BUDGET_BYTES`). A new recording prunes
when it opens and again when it closes, oldest first by the time in its
header, and a replay whose header will not read counts as the oldest.
Once one replay does not fit, every older one goes with it. Only
`.okreplay` files are pruned, never a save. The page keeps browser
storage to the same two numbers by the files' modification times, after
every copy out and before it reads the saved games in, and it removes a
pruned file from the running game's filesystem too, so nothing copies it
back. A replay in storage past the 16 MB guard is pruned and never read
in. `scripts/test_shell_replays.js` checks the page's numbers against
`tak_replay.h`.

## The file

All numbers are little endian. The header is 576 bytes:

| Bytes | Field |
|---|---|
| 8 | `OKREPLAY` |
| 2, 2 | format version (1), header size |
| 4 | `TAK_ENGINE_BUILD_ID` |
| 8, 8, 40 | data schema, content and the five group hashes |
| 32 | map fingerprint |
| 1, 1, 1, 1 | flags, the recording seat, a match's turn ticks, spare |
| 8 | when it was recorded, UTC seconds |
| 96, 32 | map name and the map's kingdom |
| 4, 4, 8 | seed, units per side, the eight rule toggles |
| 8 x 38 | each seat's kind, side, team, colour, difficulty, start and name |
| 4, 4 | last tick and command count, written on close |
| 4 | FNV-1a of the 572 bytes before it |

The flags say whether it was a match, whether the map fingerprint is
present, and whether the recording closed.

After the header come records. Each is a tag byte and the ticks since
the previous record as an unsigned LEB128 of at most five bytes:

- command: the seat, the wire length as a LEB128, and the command in the
  wire format the relay carries (`TAK_CommandSerialize`)
- checkpoint: the simulation hash after that tick's orders ran, and the
  FNV-1a of every record byte before this record
- end: the FNV-1a of every record byte before it

A checkpoint is written every 60 ticks, the cadence a match already
hashes at, so a match computes one hash for both. No record may name a
tick more than 60 past the last checkpoint, and none past eight hours at
60 Hz (`TAK_REPLAY_MAX_TICKS`). A busy hour of a match is a few hundred
kilobytes. The writer stops taking commands at 16 MB, at eight hours, or
at a tick no checkpoint reaches, and the file then ends at the last tick
it can vouch for.

## Reading one back

The reader first refuses a file larger than 16 MB, which costs one seek,
and a header whose fields fall outside what the engine has: a seat's
kind, side, team, colour, difficulty and start, the units per side, the
rule toggles, a match's turn length, the flags, a local seat that is
empty, a battle with no one in it, a last tick past eight hours, and a
map name that is not a plain name. Then it walks the whole stream once
before any world is built, a window of 8 KB at a time, and refuses a
file that is damaged anywhere or that breaks the tick rules above.
The header's checksum covers the header, and every record is under the
stream checksum that the next checkpoint or the end record carries, so
one wrong byte anywhere is caught. A closed recording must reach its end
record with the tick and count its header names and nothing after it,
so a closed file that was cut is refused. A recording that never
closed, which is what a browser tab shut mid battle leaves, plays up to
its last checkpoint and drops what came after.

Then the build and the data are checked. Determinism needs the same
engine and the same data, so a different `TAK_ENGINE_BUILD_ID`, a
different data schema or content hash, or a different copy of the map
is refused with a sentence saying which. A differing data group is
named, the way the lobby names one.

Neither the writer nor the reader allocates past its own fixed size,
about 13 KB and 11 KB, however long the battle.

The Replays list reads each file's header and nothing more, at most 64
files, so opening it costs a few hundred bytes a replay. A damaged
stream shows in the list and is refused when chosen. A recording that
never closed shows no length until then.

## Playback

The world is built from the header the way a match builds it from
START_GAME, and the local seat is the recording player's, for their fog
and their sidebar. Before each tick the commands recorded for it go into
the queue with `TAK_CmdQueue_SubmitAt`, and every local order is refused
at the one place orders leave the interface. At each checkpoint the
simulation hash is compared with the recorded one. The first that
differs is reported on the screen as the time the battle drifted from
the recording, and in the log with both hashes.

Space pauses and resumes. The = and - keys step through 1x, 2x, 4x and
8x, which scale the tick rate and never what a tick does. The camera and
the selection are free.

## Tests

`test_replay` is data free: a round trip of header and records, a cut at
every length and a damaged byte at every offset, a format, build and
data mismatch, the size guard, and the writer's and reader's memory
staying flat over twenty thousand commands. `test_command_pipeline`
records a short two seat battle in the synthetic world through the real
recorder and plays it back through the real player, and the simulation
hash matches at every turn. It also slips in one order the recording
never had and checks the drift is reported at the next checkpoint.
