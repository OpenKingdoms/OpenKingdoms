## 1. Veteran rank icons — HUD widget, NOT an on-unit overlay

### Legacy mechanics (confirmed)
- Level: the veteran-level getter at :232934 *(tool-assigned `Minimap_GetSize` —
  misleading)*. FBI `noveteran` (parsed :163080) forces level 0; otherwise a non-zero
  per-unit override float yields the cap directly; otherwise level = the unit's accumulated
  experience divided by the def's `experiencepoints`, clamped to the cap (:232945-232948).
- **OPEN `.data` constants RESOLVED** (read from the retail executable's
  `.data` section, VA 0x6188b8/0x6188bc, operands verified in the
  machine code of :232934/:232971 at file offs 0x11931c/0x1193cc). The names below are our
  labels — the binary carries no symbols:
  - the veteran multiplier step = 0.1f → mult = 1.0 + 0.1 × level (:232983), max 2.0.
  - the veteran level cap = 10. (Arasword.bos gold thresholds — swaps above level 4 and
    above level 9 — fit a 0..10 range.)
- Display has exactly TWO legacy channels — there is NO rank chevron drawn over the unit
  in the world:
  1. **HUD "Experience" widget** (manual calls it the Experience Shield): araingame.gui:86-103
     — type-19 Static named `Experience`, rect (491,454) 11×22, 3 states =
     `GuagesElements.gaf` anim `UnitLevels` frames 0/1/2 (13×22, entry [6] of
     data/anims/guageselements.gaf). Same widget in tar/ver/zon ingame guis (:92/:332).
     Updater = the HUD unit-info refresh at :152219 *(tool-assigned
     `NetPacket_Method06` — misleading; this is HUD code, not networking)*, at
     :152440-152450: it reads the unit's veteran level; level 0 hides the widget; otherwise
     the widget's current anim is set to level − 1 and it is made visible (the frame is
     clamped to the 3 authored states).
  2. **Gold model pieces via COB**: unit scripts read `get VETERAN_LEVEL` (port 32, raw
     level — :223313, the port-32 case) and show/hide gold variants (Arasword.bos
     :5241-5295: above level 4 → Torso5/ArmUL5/ArmUR5, above level 9 → Sword10). Engine
     work = correct port 32 only.
- Kill tally: on a kill the killer's own kill counter increments and its experience grows by
  the victim's `experiencepoints`; no self- or team-kill credit (:227303-227328). The HUD
  `KillCount` label shows the count as text only when the owner is the local human and the
  count is > 0 (:152496-152506).

### Our gaps
- Port 32 stubbed to 0 — src/render/units.c:3140-3145.
- `noveteran` not parsed (only `experiencepoints` → kill_xp_value, units.c:1825).
- No level accessor; no HUD wiring; **live bug**: the Experience widget currently renders
  its max frame permanently — gui_render.c pick_frame default returns frame 2 for ≥3-frame
  non-button widgets (:305-307) and hud.c never hides/overrides "Experience".
- No per-unit kills counter (credit_kill units.c:479-495 adds xp only).

### Edits

   Add constants `TAK_VETERAN_LEVEL_CAP 10`, `TAK_VETERAN_MULT_STEP 0.1f` (cite .data

## 2. Combat-start sound — the under-attack alarm pair

### Legacy (confirmed; corrects digs ssf §B.1)
- **`underattack_sound` is a PER-SIDE key in gamedata/SIDEDATA.tdf, not per-unit FBI.**
  Read inside the SIDE%d loop of the sidedata loader (:164562-164580 open/iterate;
  :164683 reads `underattack_sound`, :164709-164710 `underattack_delay`, default double
  30.0). Shipping data: every SIDE0-6 has `underattack_sound=AlarmAra`,
  `underattack_delay=30`. WAVs exist: english/Sounds/ALARMARA.WAV + ALARMMON.WAV.
- Trigger site = tail of the per-unit attack-processing update (:15222-15236): fires when
  the unit belongs to the LOCAL player, a mission flag (bit 7) is clear, and the unit has a
  recorded enemy attacker — the attacker's player slot is stamped onto the unit when damage
  lands (:227214-227216) and differs from the owner, or the unit's under-attack flag is set.
  Then:
  - if the def has the commander flag (FBI `commander`, :163074-163075) →
    play "AlarmMon" non-positionally at priority 7, volume 0x7f, under a GLOBAL 15000 ms
    rate limit (:221328-221340 *(tool-assigned `Sound_Init` — misleading)*).
  - else, only if the unit is NOT a member of the engine's selectable-unit id list
    (:237338-237356 — the same list band-box selection reads, :237483, so it reads as the
    on-screen/selectable set; i.e. the alarm is for OFF-SCREEN units): play the side's
    `underattack_sound`, rate-limited by `underattack_delay` seconds on a global timer
    (:221298-221324 *(tool-assigned `Sound_FadeIn` — misleading)*).
- No "first-contact sting" exists — this alarm pair IS the distinct combat-begin sound.

### Edits
1. src/sound/game_sound.c: add
   `void GameSound_UnderAttackAlert(int is_commander, int on_screen);`
   - loads once per battle: local side's `underattack_sound`/`underattack_delay` from
     sidedata.tdf (reuse the SIDE%d-scan pattern of loading.c:78-105, match by side name;
     defaults "" / 30.0).
   - two static ms timestamps (SDL_GetTicks): commander → play "AlarmMon" if
     now ≥ next_mon, next_mon = now+15000; else if !on_screen → play side wav if
     now ≥ next_ua, next_ua = now + delay*1000.
   - playback = existing non-positional path (GameSound_PlayUI loader, Sounds/<name>.wav,
     center pan, vol 0x7f; note legacy prio 7 for the channel-steal rule when soundclass
     priorities land). Declare in include/tak_game_sound.h.
2. src/render/units.c `unit_on_damaged` (:500): before the retarget early-outs (only the
   victim->alive/shooter/enemy checks apply), when `victim->player_id == 1`:
   `on_screen` = victim world pos inside cam rect (world->cam_x/y,viewport_w/h);
   `GameSound_UnderAttackAlert(def->commander, on_screen)`.
   Deviation note: legacy re-fires from the per-frame attack update while the attacker
   record persists; ours fires per damage event — audibly identical under the 15 s/30 s
   rate limits.
3. Doc fix: digs ssf §B.1 gap (6) — reword "per-unit underattack_sound FBI key" →
   per-side SIDEDATA key (this file is the cite).
4. Test: unit test on the rate-limiter (mock ticks); manual: skirmish, let AI hit an

## 3. ARAKING cape — transforms CORRECT, our piece DRAW ORDER is inverted

### Verdict: NOT legacy-consistent — real bug, one-line-class fix. Not the transforms.

### Evidence the cape motion itself is right
- Hierarchy (probe_3do araking.3do): Torso → Cape1 → Cape2 → Cape3 → Cape4 chain,
  offsets (0,+816773,+207255)/(0,−552211,+206255)/(0,−783915,−11717)/(0,−801995,−18020)
  — drapes down the back (+z = back in the LH model frame). COB pieces 17-20 map by name.
- Walk keyframes (cob_inspect --disasm --script walk, pieces 17-20, TA-angle→deg):
  Cape1 x 0..+9°, Cape2 x 0..+24° (z −3..0°), Cape3 x −20..+18°, Cape4 x −30..+32°,
  stepped per ~66 ms SLEEP. Cumulative chain angle (anchor→tail) stays ≥ ~0° every
  keyframe → with script-positive-x = swing BACKWARD, the cape never crosses the torso
  plane (worst frame ≈ chain z +0.5..+0.9M units behind torso center).
- Sign check: compose_node_xforms (units.c:4940 negated ANGLE_TO_RAD, Rx block
  :4991-5000) gives script +x on a down-hanging child → +z (back) — the exact convention
  the knee oracle validated (axis-conjugation dig). So mid-walk interpenetration is not
  produced by the authored data or by our transform math.

### The actual legacy draw order (this is the miss)
The model rasteriser (:197561) iterates model NODES in **REVERSE flat-table order**: the
loop starts at the last node in the table (:197658-197661) and steps backwards one node per
iteration down to node 0 (:197944-197946). Within a node, prims run FORWARD
(:197793-197799 init, :197938-197941 increment), skipping the node's first prim when the
node declares a selection primitive (:197794-197797; the vertex pass applies the same skip,
:197712-197715). Backface rule: cull cross ≥ 0 → draw (:197804-197807). The node table is
the 3DO file's DFS order with root first (the COB host's show/hide indexes it directly,
:223432-223463).

So for araking legacy paints: legs → shoulders → Head → **Cape4..Cape1** → blood emitters
→ Sword/hands/arms → **Torso** → Hip → root. The TORSO draws AFTER the capes and covers
them wherever they overlap — cape interpenetration is invisible by construction; the cape
shows only outside the body silhouette.

Our renderer replays **FORWARD** DFS (bake_emit tri_seq units.c:2297-2305 global
`seq_counter`; consumed by tri_cmp_far_first sorts at :5250-5258 single-unit, :5326-5337
merged per-unit, :5560-5581 ghost). Torso (DFS 2) draws before Cape1-4 (DFS 14-17), so
every mid-swing cape quad paints ON TOP of the torso = the reported "cape clips into his
body". The rationale comment at units.c:5211-5222 ("artists authored capes over torsos")
is a misreading — legacy order is child-first/parents-last, i.e. reversed.

   reverse-node key preserving forward prim order within a node:
   `tri_seq[...] = (uint32_t)(UNIT_MESH_MAX_NODES - 1 - node_dfs_idx) * 4096u
                   + node_local_seq++;`
   (`node_dfs_idx` = this_node_idx already in scope, :2267; add a per-call local counter
   — each bake_emit invocation is exactly one node. 64 nodes × 4096 prims stays float-
   exact for the TriSort.key cast at :5250.) Drop/repurpose seq_counter.
   All three sort paths pick the new order up unchanged.
2. Fix the comment block :5211-5222 (and the mirror comment near :5150-5160) to state
   the reverse-node rule with the cites above.
3. Optional parity nit (same pass or follow-up): skip the selection primitive like legacy
   (:197794-197797) — 3DO per-node selection_prim index (araking AraGP prim[0], the
   4-vert FLAT ground plate). Requires plumbing sel_prim from tak_obj3d parse into the
   bake and skipping that prim's fan.
