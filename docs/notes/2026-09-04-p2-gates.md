# P2: Gates never open/close, and units walk through closed gates

Status: diagnosed. Legacy mechanism fully recovered from behavioural analysis of the retail
binary plus a reading of the shipped arangate.cob script.

Legacy sections describe behaviour derived from analysis of the retail binary. `:NNNNN`
citations are evidence pointers into a private reference that is not distributed. They
mark where a claim can be re-checked by whoever holds it, and nothing here reproduces
that file's expression. Symbol names marked *(tool-assigned, misleading)* are automatic
labels that do **not** describe what the routine does. The description beside them does.
Fenced blocks and the §3 edit list are TAK-RE implementation (proposed).

## 1. Symptom

ARANGATE (and tarngate/verngate) doors never animate, gates never block anything, and no
auto-open happens. Root causes, in order of severity:

1. **No occupancy layer at all.** Movement and A* consult terrain only.
   `unit_terrain_walkable` (src/render/units.c:3449-3476, used at :3610 and :3693) and
   `cell_walkable_slow` (src/game/pathing.c:113-154) call `Terrain_IsWalkable`
   (src/render/terrain.c:257-309), which tests slope + map **features** only. Buildings
   (gates included) imprint nothing, so *every* unit walks through *every* building.
2. **YARD_OPEN port is a dead bit.** `cob_host_set_unit_value` case 18
   (src/render/units.c:2927) stores `u->cob_yard_open` and nothing consumes it. Legacy SET
   YARD_OPEN re-imprints the map and can *refuse* the set (see §2.3).
3. **Nothing ever triggers the gate's COB Activate/Deactivate.** The only Activate caller is
   the activatewhenbuilt path (src/render/units.c:4708-4714). Legacy auto-toggles gates from
   a per-tick proximity scan (§2.5). Gate FBIs don't set activatewhenbuilt.
4. **No yardmap / gate / onoffable parsing.** `yardmap` appears nowhere in src/. arangate.fbi
   (data/extracted/data/units/arangate.fbi): `gate=1`, `onoffable=1`, footprint 14×4,
   `yardmap = ooooccccccoooo` ×4. The six `c` columns are the gateway.
5. BUGGER_OFF port 19 unhandled: SET warns (units.c:2930-2934), GET returns 0 (units.c:3111).
   arangate.cob's OpenYard/CloseYard retry loop uses it.

## 2. Legacy mechanism

### 2.1 Yardmap parse (:163207-163293)
The `yardmap` string is parsed into a per-def byte array sized footprint_x × footprint_z,
where the footprint comes from the resolved move class (:163193-163195). The char→byte
mapping is a table at :163223-163256. Strings shorter than the footprint repeat their last
char, and mobile units are given an all-0x29 map instead (:163272-163292):

| char | byte | movement semantics (bits 1/2) |
|------|------|-------------------------------|
| `.`  | 0x00 | never blocks |
| `y`  | 0x29 | never blocks (walkable yard) |
| `Y`  | 0x31 | never blocks |
| `c`  | 0x2d | bit2 only → blocked when yard **closed**, open when open (gateway cells) |
| `C`  | 0x35 | blocked when closed |
| `o`  | 0x2f | bits1+2 → always blocked |
| `O`  | 0x2b | bit1 → blocked when yard **open** only |
| `w`  | 0x37 | always blocked |
| `S`  | 0x8f | always blocked + def flag bit31 (:163236-163237) |
| `f`  | 0x6f | always blocked (feature cell) |

**Blocking rule: a cell blocks when its yardmap byte has bit 0x02 set and the yard is open,
or bit 0x04 set and the yard is closed.** The tested bit is selected by the yard's
open/closed state (see :217987-217988, :218170, :219021, which select it branchlessly).
FBI `gate=1` sets a def flag (:163110-163112), and `onoffable` sets another
(:163023-163024).

### 2.2 Imprint: the map-cell imprint pass, :217912-218035
Each map cell records the id of the unit occupying it. On the building path
(:217974-218031): for each footprint cell, if the yardmap byte blocks under the current
open/closed state the cell takes this unit's id (evicting/marking conflicts). Otherwise the
cell is cleared if and only if it still holds this unit's id (:217989-217991). On a `gate=1`
def, every cell that blocks *only when closed* (the `c`/`C` bytes, bit 0x04 set and bit
0x02 clear) is additionally tagged as a **gate cell** (:218012-218018). Movement and placement
queries read those ids: the move-cost query at :218984-219042 and the build-placement search
at :219098-219148.

### 2.3 COB SET YARD_OPEN: refusable, re-imprints
The COB set-value dispatcher's port-18 case (:223375-223378) routes to the yard-state setter
at :219046-219059 *(tool-assigned name `MapLoader_SetTile`, misleading: it is not map
loading)*:
1. The move-cost query (:218984-219042) scans the cells that would become blocked under the
   NEW state (:219021 picks the open/closed bit). If any **other** live unit is imprinted on
   one of them the call reports failure → the **set is refused silently** (GET 18 keeps the
   old value).
2. On success the unit's yard-open state is written (:219053), a dirty flag is set, the
   footprint is re-imprinted, and the pathfinder is notified that blocking changed
   (:219054-219056).

GET 18 reads back that same stored state (:223284-223285). SET/GET 19 (BUGGER_OFF) is a
separate per-unit flag stored alongside it (:223379-223381, :223286-223287).

### 2.4 Gate COB (arangate.cob, disasm via `build/src/Debug/cob_inspect.exe scripts/arangate.cob --disasm`)
- `Activate` (pc2127) → start `RequestState(0)`. `Deactivate` (pc2134) → `RequestState(1)`.
- `RequestState` (pc1946): a static state machine. When wanted!=current it loops
  `Go`/`Stop`, and re-entrant calls just overwrite the wanted state.
- `Go` (pc1904): call `open` (door anim, 3s), HIDE Door1/Door2, call `OpenYard`.
- `OpenYard` (pc718): sets port 18 to 1. While GET 18 still reads back 0 it raises BUGGER_OFF
  (port 19 = 1), sleeps 1500 ms and re-issues the set. Once GET 18 reads 1 it clears
  BUGGER_OFF. The engine's refusal is what drives the retry loop, with BUGGER_OFF
  raised for its duration. `CloseYard` (pc751) is the mirror.
  **Port 18 SET must be refusable and GET must reflect it.**
- `Create` (pc2009) waits `GET 17` (BUILD_PERCENT_LEFT) == 0, then InitState (closed).

### 2.5 Auto-open: the AI brain tick :19003-19011 + the gate update :15260-15361
Every brain tick, units whose def carries the gate flag run the gate update:
- Scan map cells of **footprint + 1-tile border** (loops −1..fp inclusive, :15286-15330).
  A cell holding a live unit of the **same owner** (:15300) that is mobile (:15301)
  → want-open (:15302-15305).
- Also want-open while any such unit's own footprint covers a cell tagged as a gate cell
  (:15307-15323), so it never closes on top of someone.
- Edge-triggered against the unit's stored activation state: closed+want → issue `Activate`
  order, and open+none → `Deactivate` (:15333-15359). The state-toggle path (:236384-236422) is
  what actually runs the COB `Activate`/`Deactivate` threads, on the rising/falling edge
  (:236399-236406).

### 2.6 Pathfinder plans THROUGH own closed gates (:21986-22032)
When the path cost classifier hits a cell in a blocked class it checks whether the cell is
tagged as a gate cell and imprinted by a live `gate=1` unit. If so the cell is reclassified
by ownership: **your own gate becomes passable, cost class 4** (auto-open handles arrival),
while a foreign gate stays blocked. Related: wall/gate defs are the `bmcode==1` linear build
class (digs combat §8, :150077-150086, :162924). A manual gate-toggle order exists at
:151290-151300 (the `onoffable` button issues Active/Inactive).

## 4. As built: corrections to §2/§3

Verified against the legacy reference while implementing. The edit list
above is the pre-implementation plan; these points differ.

1. **Auto-open needs the unit to be *moving*.** §2.5 says "a same-owner
   mobile unit in the ring opens the gate". The condition is stricter:
   the unit must have a non-zero speed (:15302 tests the mover's speed
   field), *or* its own footprint must cover a gate cell (:15307-15323).
   A parked friendly next to a gate does not hold it open unless it is
   standing in the gateway.
2. **No stall in front of an own gate (§E7 is wrong).** The cost
   classifier returns "passable" for an own gate cell (:21986-22032),
   and the move step keeps gate blockers in a list separate from hard
   blockers (:219336-219340). Own units simply walk through their own
   closed gate; the doors animate open around them. Stalling instead
   would deadlock, because the auto-open wants a *moving* unit.
3. **BUGGER_OFF has no engine consumer.** Port 19 is written by SET
   (:223379-223381) and read back by GET (:223286-223287) and nothing
   else in the binary reads that bit. It exists only so the gate script
   can flag "I am retrying". §E4's idea of pushing units out on the
   rising edge is not legacy.
4. **What actually frees a trapped unit is the imprint yield.** A
   footprint cell already held by another live unit is skipped and the
   structure re-marks itself dirty to retry (:217994-218006, retried
   from :217924). The cell stays the unit's until it walks off.
5. **Mobile units imprint too.** The same map cells carry a moving
   unit's footprint (:217933-217971), and the move step refuses a cell
   another unit holds (:219329-219340). The *planner* never sees them:
   only the yard setter notifies the pathfinder cost map (:219056), so
   routes are planned through crowds and resolved at move time.
6. **Move-class defaults are seeded before parsing** (:187361-187377):
   MaxWaterDepth 10000, MinWaterDepth -10000, slopes 255, then MaxSlope
   is capped by MaxWaterSlope and BadSlope by MaxSlope (:187452-187457).
   The shipped water classes omit MaxWaterDepth, so a 0 default makes
   every water cell illegal for boats.
7. The manual open/close order is held against the auto scan for 10 s.
   Legacy re-asserts on the next brain tick; holding it is a deliberate
   deviation so a player's click is visible through the 3 s door
   animation.
